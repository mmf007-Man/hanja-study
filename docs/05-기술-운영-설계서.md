# 기술 및 운영 설계서

작성일: 2026-11-21 / 기준 데이터 버전: `0.2.0` (`schemaVersion: 1`) / 대상 앱: 1차 정적 웹앱(로컬 저장) → 2차 서버 동기화 확장형

본 문서는 [작업 체크리스트](00-작업-일정표.md)의 `06 기술과 개발 계획` 및 트랙 A에서 확정된 기술·범위 결정을 바탕으로, 본 앱의 프론트엔드 아키텍처, 핵심 엔진 모듈, `LocalStorage` 데이터 모델, 백업/마이그레이션, 정적 호스팅 운영·보안·비용 계획을 정의한다.

## 1. 아키텍처 개요 및 확정 범위

### 1.1 1차 버전(MVP)과 2차 확장 방향

| 구분 | 1차 버전 (서버/로그인 없음, 월 0원) | 2차 확장 버전 (클라우드 동기화) |
|---|---|---|
| 실행 구조 | **100% 클라이언트 사이드 정적 웹앱** | 정적 프론트엔드 + 경량 API/DB 백엔드 |
| 사용자 식별 | 한 기기 내 **가족 프로필 전환**(이름·아바타) | 보호자 로그인 + 가족 그룹 초대·권한 |
| 데이터 저장 | 브라우저 `LocalStorage` + **JSON 내보내기/가져오기** | 원격 클라우드 DB 동기화(`StorageAdapter` 교체) |
| 학습 기능 | 일반 학습(4유형 혼합), 오답 복습, 기기 내 하루 도전 | 온라인 가족 주간 순위 경쟁, 서버 채점·중복 제출 방지 |
| 콘텐츠 범위 | 천재교과서 중학 한문(안대회) 20단원 637자 | 급수 시험(한국어문회 등) 데이터 확장 |
| 대상 기기 | 모바일 터치(iOS Safari · Android Chrome) + PC(Chrome · Edge) | 동일 (멀티 디바이스 기록 공유) |

### 1.2 핵심 설계 원칙

1. **저장소 추상화(`StorageAdapter`)**: UI와 학습 엔진은 저장 매체를 직접 알지 못하며, `StorageAdapter` 인터페이스만 호출한다. 1차에서는 `LocalStorageAdapter`를 사용하고, 2차에서는 `RemoteStorageAdapter`로 교체·병행한다.
2. **규칙 문서와 데이터 규격의 단일 진실 원천**: 출제·채점·복습 규칙은 [학습과 채점 및 획 보정 명세서](02-학습-채점-획보정-명세서.md)를, 데이터 형식과 무결성 기준은 [데이터 안내](../data/README.md) 및 [validate_data.py](../scripts/validate_data.py)를 그대로 따른다.
3. **기존 획 엔진 자산 재사용**: [stroke-engine.js](../prototype/stroke-assist/js/stroke-engine.js)(`1024×1024` Top-Down 기준, 637자 / 5,932획 100% 통합 테스트 통과)를 본 앱의 핵심 판정 엔진으로 승계한다.

> **참고**: `prototype/stroke-assist`는 빌드 없는 순수 HTML/Vanilla JS로 검증 편의성에 집중했으나, 본 앱에서는 4유형 혼합 세션·복습 큐·가족 프로필·백업 가져오기/내보내기 상태가 복합적으로 얽히므로 **Vite + React + TypeScript**로 전환하여 런타임 상태 오류를 컴파일 단계에서 차단하는 편이 유지보수에 유리하다.

### 2.2 정적 JSON 데이터 번들 및 지연 로딩 전략

현재 저장소에 실측된 핵심 데이터 크기는 다음과 같다.

| 파일 | 실물 크기(raw) | 포함 내용 | 로딩 전략 |
|---|---:|---|---|
| [chunjae-middle-hanja-2022-ahn.json](../data/textbooks/chunjae-middle-hanja-2022-ahn.json) | 20,650 B (~20 KB) | 20단원 메타·단원별 `characterIds` 순서 | **초기 부트스트랩 시 로드** (앱 진입 즉시 단원 선택 UI 구성) |
| [characters.json](../data/characters.json) | 348,580 B (~340 KB) | 637자 기본 정보, 642개 독음 쌍, 29자 `allowedSounds`, `strokeData` 메타 | **초기 부트스트랩 시 로드** (gzip 전송 시 ~60–80 KB 수준, 메모리 `Map<id, Character>` 인덱싱) |
| [normalized_strokes.json](../data/strokes/normalized_strokes.json) | 3,497,621 B (~3.34 MB) | 637자 전체 Top-Down `1024×1024` SVG `strokes` 및 `medians` (총 5,932획) | **지연 로딩(Lazy Loading)** — 초기 번들 포함 금지 |

**획 데이터 지연 로딩 설계**:
1. **빌드 타임 분할(권장)**: Vite 빌드 전처리 스크립트로 `data/strokes/normalized_strokes.json`을 단원별(또는 글자별/블록별) JSON 청크(예: `public/data/strokes/chunks/unit-01.json` ~ `unit-20.json`, 단원당 약 100~200 KB)로 분할 생성한다.
2. **온디맨드 프리페치**: 사용자가 쓰기 유형을 포함한 학습 회차를 시작하면, 해당 회차에 배정된 한자의 획 데이터만 `fetch`하여 인메모리 캐시(`Map<character, StrokeEntry>`)에 적재한다.
3. **단일 번들 폴백**: 단원 청크 분할 전 단계에서는 `normalized_strokes.json`을 비동기 `fetch`한 뒤 브라우저 HTTP 캐시 / Cache API에 보관하며, 객관식·주관식만 진행할 때는 네트워크에서 내려받지 않는다.

## 3. 저장소 추상화(`StorageAdapter`) 설계

1차 로컬 저장과 2차 원격 DB 연동을 분리하기 위해 모든 영속성 접근은 비동기 인터페이스 `StorageAdapter`를 경유한다.

```ts
export interface StorageAdapter {
  readonly mode: 'local' | 'remote';

  // 프로필 관리
  listProfiles(): Promise<UserProfile[]>;
  saveProfile(profile: UserProfile): Promise<UserProfile>;
  deleteProfile(profileId: string): Promise<void>;
  getActiveProfileId(): Promise<string | null>;
  setActiveProfileId(profileId: string): Promise<void>;

  // 학습 회차 & 이어하기 스냅샷
  getActiveSession(profileId: string): Promise<SessionSnapshot | null>;
  saveActiveSession(profileId: string, snapshot: SessionSnapshot): Promise<void>;
  clearActiveSession(profileId: string): Promise<void>;
  appendCompletedSession(profileId: string, summary: CompletedSessionRecord): Promise<void>;
  listCompletedSessions(profileId: string, limit?: number): Promise<CompletedSessionRecord[]>;

  // 뜻·음 쌍 개인 누적 출제 이력
  getExposureStats(profileId: string): Promise<Record<string, ReadingExposureStat>>;
  recordReadingExposure(profileId: string, readingKey: string, exposedAt: string): Promise<void>;

  // 오답 복습 큐
  getReviewQueue(profileId: string): Promise<Record<string, ReviewItem>>;
  upsertReviewItems(profileId: string, items: ReviewItem[]): Promise<void>;

  // 하루 도전
  getDailyChallenge(profileId: string, dateKey: string): Promise<DailyChallengeRecord | null>;
  saveDailyChallenge(profileId: string, record: DailyChallengeRecord): Promise<void>;

  // 백업 & 마이그레이션
  exportBackup(): Promise<AppBackupPayload>;
  importBackup(payload: AppBackupPayload, strategy: 'replace' | 'merge'): Promise<void>;
}
```

- **1차 구현 (`LocalStorageAdapter`)**: 위 메서드를 `window.localStorage` 기반 동기 직렬화 + `Promise.resolve(...)`로 구현한다.
- **2차 구현 (`RemoteStorageAdapter`)**: 동일 인터페이스를 REST/RPC API 호출로 구현하며, 오프라인 임시 버퍼링이나 최초 1회 로컬→원격 백업 업로드(`importBackup`)를 지원한다.

## 4. 핵심 모듈 설계

### 4.1 데이터 카탈로그 & 인덱스 모듈 (`CatalogStore`)

- `characters.json`에서 `readingStatus === 'verified'`인 한자만 뜻·음 문제 후보로 등록한다([data/README.md](../data/README.md) 기준).
- 쓰기 문제 후보는 `readingStatus === 'verified'` **AND** `strokeStatus === 'verified'` **AND** 획 데이터 로드 가능 조건을 모두 만족하는 한자만 포함한다. (현재 `characters.json` 637자는 `strokeStatus: "draft"` 상태이므로 Phase 03 실기기 테스트 완료 후 `verified` 승격분부터 활성화된다.)
- `chunjae-middle-hanja-2022-ahn.json`의 `units[].characterIds` 배열 순서를 그대로 유지하며, 임의 정렬하지 않는다.

### 4.2 세션·출제 엔진 (`SessionEngine` & `QuestionGenerator`)

#### A. 일반 학습 20문항 구성 및 유형 혼합
1. **기본 문항 수**: 1회차 총 **20문항** (뜻·음 동시 질문도 1문항으로 계산).
2. **유형 균등 배분**: 선택한 유형 집합 $T \subseteq \{\text{hanja\_to\_choice}, \text{hanja\_to\_input}, \text{reading\_to\_choice}, \text{reading\_to\_write}\}$ ($1 \le |T| \le 4$)에 대해 몫 $q = \lfloor 20 / |T| \rfloor$, 나머지 $r = 20 \bmod |T|$로 배분한다.
   - 1유형: 20문항 / 2유형: 10·10 / 3유형: 7·7·6 / 4유형: 5·5·5·5.
   - 배분 수 확정 후 Fisher-Yates 셔플로 출제 순서를 무작위로 섞는다.
   - 3유형 선택 시 남는 2문항(+1, +1)은 고정 우선순위 또는 세션 시드 무작위 배정 중 일관된 기준을 적용한다.
3. **20자 이상/미만 중복·반복 처리**:
   - 선택한 단원의 출제 가능 한자가 **20자 이상**이면 같은 회차 내 한자 중복을 허용하지 않는다.
   - **20자 미만**($N < 20$)이면 선택 단원 범위 내에서 1라운드 전수 출제 후, 누적 출제 횟수가 적은 한자 순(직전 연속 중복 금지)으로 반복 출제해 20문제를 채운다. **정답 한자를 다른 단원에서 가져오지 않는다.**
4. **출제 불가 사전 검사**: 선택한 유형 중 출제 가능 한자가 0자이거나 4지선다 보기 구성이 불가능하면 시작 전 불가 사유를 안내하고 시작 버튼을 비활성화한다.

#### B. 객관식 4지선다 보기 구성 및 중복 정답 방지
- **한자 → 뜻·음 객관식 (`hanja_to_choice`)**:
  - 정답 쌍 1개를 아래 `ReadingPairSelector`로 선택하고, 뜻 보기 4개 / 음 보기 4개를 각각 생성한다.
  - 오답 후보에서 **해당 한자의 다른 올바른 뜻·음, 동일 쌍의 복수 `meanings`, 등록된 `allowedSounds`**를 전부 제외한다.
  - 선택 단원 우선 추출 → 3개 미만 부족 시 같은 교과서 다른 단원에서 보충한다.
- **뜻·음 → 한자 객관식 (`reading_to_choice`)**:
  - 제시문은 해당 한자의 **교과서 수록 모든 뜻·음 쌍**을 묶음별로 표시한다(예: `즐겁다 · 락 / 노래 · 악`).
  - 오답 한자 3개 추출 시 제시한 뜻·음 쌍 중 하나라도 일치하는 다른 정답 한자(동음이의·동훈 한자)는 오답 후보에서 제외한다.
  - 선택 단원 우선 → 부족 시 같은 교과서 타 단원에서 보충하며, 최종 보기 4개가 모두 서로 다른 한자이고 정답이 정확히 1개인지 어설션 검증한다.

#### C. 복수 독음 쌍 우선순위 및 최초 표시 카운트
- 한자 → 뜻·음 객관식 출제 시 한자에 독음 쌍이 2개 이상이면 다음 비교 순서로 정답 쌍을 선정한다:
  1. `exposureCount` 오름차순 (개인 누적 출제 횟수가 가장 적은 쌍 우선, 미출제는 `0`, 교과서 전체 단원 기준)
  2. `lastExposedAt` 오름차순 (횟수 동률 시 마지막 출제 시각이 더 오래된 쌍 우선; `null`은 최우선)
  3. 완전 동률 시 타이브레이커: 무작위 선택
- **카운트 증가 시점**: 문항이 미리 생성될 때가 아니라 **학습 화면에 해당 문항이 최초 렌더링(노출)될 때** `exposedQuestionIds`에 `questionId`를 기록하며 1회만 증가시킨다. 새로고침·이어하기 재진입 시 이미 `exposedQuestionIds`에 있으면 중복 증가하지 않는다.

#### D. 하루 도전 (`DailyChallenge`)
- `dateKey` (`YYYY-MM-DD`, 로컬 날짜 기준)를 시드로 하는 결정적 난수 생성기(예: Mulberry32)를 사용해 기기 내 모든 가족 프로필이 **같은 날 동일한 20문항 세트(유형·한자·보기 순서)** 로 도전한다.
- 프로필당 하루 1회 공식 기록을 `DailyChallengeRecord`에 저장해 기기 내 가족 간 일일 점수·정답률·소요 시간 비교에 활용한다(2차 서버 전환 시 서버 출제·서버 채점·주간 순위로 확장).

### 4.3 채점 엔진 (`GradingEngine`)

1. **공백 정규화**: `normalizeAnswer(s) = s.replace(/\s+/g, '')` (앞뒤 및 중간 공백 모두 제거, 표시용 원문은 유지).
2. **제출 가능 조건 검증 (`canSubmit`)**:
   - `hanja_to_choice`: 뜻 보기 선택값 `!== null` AND 음 보기 선택값 `!== null`.
   - `hanja_to_input`: `normalizeAnswer(meaningInput).length > 0` AND `normalizeAnswer(soundInput).length > 0`.
   - `reading_to_choice`: 선택 한자 `!== null`.
   - `'모르겠어요'` 버튼은 입력 상태와 무관하게 항상 활성화되며, 클릭 즉시 해당 문항을 확정한다.
3. **한자 → 뜻·음 채점 로직**:
   - **객관식**: 선택한 뜻이 정답 쌍의 `meaning`과 같으면 `meaningCorrect = true`, 선택한 음이 정답 쌍의 `sound`와 같으면 `soundCorrect = true`. 둘 다 `true`일 때만 `2점`, 그 외 `0점`.
   - **주관식 (복수 독음 & 허용 답안 포함)**:
     - 각 `reading` 묶음 $R_i$에 대해:
       - `meaningMatched_i`: `normalizeAnswer(meaningInput)`이 $R_i.\text{meanings}$ 중 하나와 공백 제거 후 **완전 일치** (동의어·어미 변형·오타 불허).
       - `soundMatched_i`: `normalizeAnswer(soundInput)`이 $R_i.\text{sound}$ 또는 $R_i.\text{allowedSounds}$ 중 하나와 **완전 일치**.
     - 어떤 $i$에 대해 `meaningMatched_i && soundMatched_i`이면 → **`pairMatched = true`**, `2점`, 정답.
     - 그렇지 않으면 `0점`이며, 개별 판정은 전체 $R$ 기준으로 기록한다:
       - `meaningCorrect = some(i => meaningMatched_i)`
       - `soundCorrect = some(i => soundMatched_i)`
       - `meaningCorrect && soundCorrect && !pairMatched` → **`errorType = 'pair_mismatch'`** (예: `樂`에 `즐겁다` + `악` 입력). 입력/선택 칸에는 주황 경고(`개별 존재하나 쌍 불일치`)를 즉시 표시한다.
       - 그 외 → `'meaning_error' | 'sound_error' | 'both_error'`.
   - **뜻·음 → 한자 객관식 및 쓰기**: 정답 2점, 오답 0점. 쓰기는 모든 획 통과 완료 시 2점(`'모르겠어요'`·중도 이탈 0점).
4. **진행 중 피드백 및 정답 공개 시점 분리**:
   - 일반 제출 문항: 채점·저장 즉시 **진행 중 정오 여부와 누적 점수**를 상단/피드백 배지에 반영하되, 틀렸을 때의 **정답 내용(해설·올바른 쌍)**은 **회차 종료 후 결과 화면에서 일괄 공개**한다.
   - `'모르겠어요'` 문항: `0점` 및 `outcome: 'dont_know'` 기록 후 **즉시 정답 공개** 및 오답 복습 등록.
   - 중도 종료 시: 이미 화면에 표시된 미제출 문항은 `'abandoned'`(중도 이탈, 0점, 오답 복습 미등록)로 기록하고 미표시 문항은 제외한다.
5. **정답률 산출 공식**:
   - **문항 정답률**: `정답 문항 수 ÷ 확정 응답 문항 수(일반 제출 + '모르겠어요')` (`'중도 이탈'` 제외)
   - **뜻·음 개별 정답률**: `개별 항목 정답 수 ÷ 일반 제출 문항 수` (`'모르겠어요'`·`'중도 이탈'` 제외, `'모르겠어요'` 별도 건수 표기)

### 4.4 복습 큐 상태 머신 (`ReviewQueueEngine`)

```
[일반/도전 학습 오답 또는 '모르겠어요']
   │ (뜻 오류 / 음 오류 / 둘 다 오류 / 쌍 불일치 / 모르겠어요)
   ▼
┌──────────────────────────────┐  연속 2회 정답 (같은 회차 내)  ┌──────────────────────┐
│ status: 'needs_review'       │ ─────────────────────────────▶ │ status: 'completed'  │
│ sessionStreak: 0 → 1         │                                │ (과거 오답이력 보존) │
└──────────────────────────────┘ ◀───────────────────────────── └──────────────────────┘
   ▲  │                            이후 일반/도전 학습에서 오답 시
   │  └─ 오답 / '모르겠어요' → sessionStreak = 0                   (이전 완료 이력 보존)
   └─ 새 학습 회차 시작 → 미완료 항목의 sessionStreak = 0 리셋
```

**핵심 구현 규칙**:
1. **복습 포함 대상 및 항목 키 분리**: 한자 → 뜻·음 객관식/주관식 오답뿐 아니라 뜻·음 → 한자 객관식 오답, 쓰기 오답, `'모르겠어요'` 문항까지 모두 복습 큐에 포함한다(`'중도 이탈'` 제외). `reviewItemId = "${characterId}::${questionType}::${targetSound}"`로 식별해 같은 한자라도 형식별(`hanja_to_choice` vs `hanja_to_input`) 독립 복습 항목으로 관리한다.
2. **객관식 복습 보기 재구성**: 틀렸던 `targetSound`·`targetMeaning` 정답 쌍은 그대로 유지하되, 매 복습 출제 시마다 오답 보기 3개와 보기 순서를 새로 생성한다(단, 진행 중 새로고침 시에는 스냅샷을 유지).
3. **출제 순서 및 1문제 간격 스케줄러**:
   - 대기열은 선입선출(FIFO)과 연속 정답 횟수가 적은 순을 조합해 출제하며, 최근 출제된 `lastReviewedItemId`를 추적해 바로 직전 항목을 연속 배치하지 않는다(`A → 다른 문제 1개 → A`).
   - 미완료 복습 항목이 1개(`A`)만 남았는데 `sessionStreak === 1`인 상태라면, 사용자가 선택한 단원(없으면 타 단원)의 **다른 한자(`B !== A.characterId`)** 로 일반 문제 1개를 동적으로 생성해 `B`를 먼저 출제하고, 그 다음 턴에 `A`를 다시 출제한다. `B`의 결과는 `A`의 `sessionStreak`에 합산하지 않으며, `B` 자체도 일반 채점·복습 등록 규칙을 따른다.

### 4.5 획 보정 엔진 및 캔버스 통합 설계 (`StrokeCanvas` & `StrokeEngine`)

기존 [stroke-engine.js](../prototype/stroke-assist/js/stroke-engine.js)와 [app.js](../prototype/stroke-assist/js/app.js)의 검증된 구조를 React 컴포넌트로 캡슐화한다.

1. **표준 좌표계와 `evaluateStroke` 파이프라인**:
   - 내부 계산 좌표계는 Top-Down `0..1024`로 통일한다([normalized_strokes.json](../data/strokes/normalized_strokes.json) 637자 전체가 이미 Top-Down으로 정규화되어 있으므로 `isTopDown: true` 전달).
   - `pointerup` 시점 1회 평가 순서:
     1) 점 개수(`< 2`) 및 최소 호 길이(`< 25px`) 필터
     2) `N = 32` 등간격 리샘플링(`resample`)
     3) 시작점 오차(`startDist`), 끝점 오차(`endDist`), 궤적 평균 유클리드 오차(`avgTrajectoryDist`), 길이 비율(`lengthRatio`), 방향 코사인 유사도(`cosineSim`, 길이 `< 70`인 점 획은 방향성 완화) 산출
     4) 역방향 감지(`isReversed`) 및 특수 글자 변별 규칙(`土`/`士` 가로획 폭, `日`/`曰` 종횡비) 검사
2. **모바일 터치 & iOS Safari 스크롤 방지**:
   - 드로잉 스테이지 래퍼와 `<canvas>`에 CSS `touch-action: none; user-select: none; -webkit-user-select: none; -webkit-touch-callout: none;`를 적용한다([style.css#L448](../prototype/stroke-assist/css/style.css#L448) 검증 패턴).
   - `PointerEvent` (`pointerdown`, `pointermove`, `pointerup`, `pointercancel`) 사용 및 `setPointerCapture(evt.pointerId)`로 손가락이 캔버스 경계 밖으로 살짝 벗어나도 획이 끊기지 않게 처리한다.
   - iOS Safari의 바운스/고무줄 스크롤 및 제스처 간섭을 막기 위해 쓰기 스테이지 내부에서 `touchstart`/`touchmove`에 `{ passive: false }` 보조 `preventDefault()`를 적용하거나 `overscroll-behavior: contain`을 결합한다.
   - `window.devicePixelRatio`를 반영한 캔버스 backing store 스케일링 및 `ResizeObserver` 기반 좌표 보정.
3. **`fill` / `stroke` 이중 SVG 레이어 렌더링**:
   - 레이어는 4층으로 겹친다: ① 격자(미자격) 배경 SVG → ② 흐린 정자 가이드/점선 힌트 SVG → ③ 통과 확정 획 SVG → ④ 사용자 실시간 필기 `<canvas>`.
   - `renderMode === 'fill'` (630자: `animcjk_ko` 382, `animcjk_hant` 177, `makemeahanzi` 58, `internal` 13): `<path d="..." fill="..." stroke="none" />`
   - `renderMode === 'stroke'` (7자: `kanjivg` — `厖`, `姉`, `顔`, `爲`, `硏`, `絶`, `郞`): `<path d="..." fill="none" stroke="..." stroke-width="54" stroke-linecap="round" stroke-linejoin="round" />`
4. **통과/실패 및 3회 실패 점선 가이드**:
   - **목표 한자 특정 제시**: 쓰기 문제 화면에는 교과서의 모든 뜻·음 쌍과 함께 부수·총획 힌트를 함께 표시해 동음·동의 한자와 혼동되지 않도록 한다.
   - **통과 시**: `<canvas>`의 사용자 입력 궤적을 짧게 강조(120ms)한 뒤 지우고, 확정 획 SVG 레이어에 정자 `<path>`를 즉시 추가한다.
   - **실패 시**: 잘못된 획을 정자로 자동 교체하지 않으며, 이전까지 통과한 획들만 유지한 채 실패 사유 피드백(시작 위치/방향/길이/`土·士` 변별 등)을 표시한다.
   - **3회 연속 실패 가이드**: 동일 `strokeIndex`에서 연속 3회 실패 시 현재 획의 점선 메디안 경로와 시작점 가이드를 자동으로 활성화하고, 가이드 사용 여부를 `AnswerRecord`에 기록한다(문항 완료 배점은 2점 통일).

### 5.1 키 네임스페이스

버전 충돌 방지 및 프로필별 격리를 위해 키 접두사 `hanja_study_v1_`를 사용한다.

| 키 | 저장 내용 | 예상 크기 |
|---|---|---|
| `hanja_study_v1_meta` | 스키마 버전, 마지막 사용 `activeProfileId`, 앱 설정(허용 오차 프리셋 등) | < 1 KB |

> **프로필당 단일 상태 키(`..._state_<profileId>`) 전략**: 한 프로필의 읽고 쓰기를 원자적 JSON 단위로 관리해 일부 키만 갱신되어 불일치가 생기는 위험을 줄인다.

### 5.2 주요 엔티티 스키마 (TypeScript / JSON)

```ts
export interface UserProfile {
  id: string;                 // 예: "prof_uuid"
  name: string;               // 표시 이름 (최대 12자)
  avatarId: string;           // 내장 아바타 아이콘 ID (예: "tiger", "rabbit")
  createdAt: string;          // ISO-8601
}

export interface ProfileLearningState {
  schemaVersion: 1;
  profileId: string;
  activeSession: SessionSnapshot | null;
  exposureStats: Record<string, ReadingExposureStat>; // key: `${charId}::${sound}`
  reviewQueue: Record<string, ReviewItem>;            // key: `${charId}::${type}::${sound}`
  dailyChallenges: Record<string, DailyChallengeRecord>; // key: `YYYY-MM-DD`
  completedSessions: CompletedSessionRecord[];        // 최근 N개(예: 100개) 보관
}

export interface SessionSnapshot {
  sessionId: string;
  mode: 'normal' | 'review' | 'daily';
  dataVersion: string;        // 출제 당시 데이터 버전 (예: "0.2.0")
  unitIds: string[];
  selectedTypes: QuestionType[];
  questions: FrozenQuestion[]; // 생성된 보기 순서·정답 쌍을 고정 저장
  currentIndex: number;
  exposedQuestionIds: string[]; // 화면 최초 표시 완료 ID 목록 (중복 카운트 방지)
  answers: AnswerRecord[];
  startedAt: string;
  updatedAt: string;
}

export interface AnswerRecord {
  questionId: string;
  characterId: string;
  questionType: QuestionType;
  targetSound: string;
  score: 0 | 2;
  outcome: 'correct' | 'incorrect' | 'dont_know' | 'abandoned';
  meaningCorrect?: boolean;
  soundCorrect?: boolean;
  pairMatched?: boolean;
  errorType?: 'meaning_error' | 'sound_error' | 'both_error' | 'pair_mismatch' | 'dont_know' | 'abandoned';
  strokeGuideUsed?: boolean;  // 쓰기 3회 연속 실패 점선 가이드 노출 여부
  submittedAt: string;
}

export interface ReviewItem {
  reviewItemId: string;       // `${characterId}::${questionType}::${targetSound}`
  characterId: string;
  questionType: QuestionType;
  targetSound: string;
  targetMeanings: string[];
  status: 'needs_review' | 'completed';
  sessionStreak: number;      // 새 회차 시작 시 0으로 초기화
  lastErrorType: AnswerRecord['errorType'];
  history: Array<{
    at: string;
    event: 'registered' | 'review_pass' | 'review_fail' | 'completed' | 'reopened';
    sessionId: string;
    errorType?: AnswerRecord['errorType'];
  }>;
}
```

### 5.3 JSON 내보내기/가져오기 백업 포맷

브라우저 캐시 삭제·기기 교체에 대비해 원클릭 JSON 파일 백업을 제공한다.

```json
{
  "exportFormat": "hanja-study-backup",
  "exportSchemaVersion": 1,
  "exportedAt": "2026-11-21T21:00:00+09:00",
  "dataVersion": "0.2.0",
  "activeProfileId": "prof_01",
  "profiles": [
    { "id": "prof_01", "name": "민수", "avatarId": "tiger", "createdAt": "2026-11-21T10:00:00+09:00" }
  ],
  "states": {
    "prof_01": {
      "schemaVersion": 1,
      "profileId": "prof_01",
      "activeSession": null,
      "exposureStats": {},
      "reviewQueue": {},
      "dailyChallenges": {},
      "completedSessions": []
    }
  }
}
```

- **가져오기(Import) 안전장치**:
  1) 파일 확장자(`.json`) 및 `exportFormat === "hanja-study-backup"`, `exportSchemaVersion` 검사.
  2) 필수 필드 타입 검증 실패 시 현재 `LocalStorage` 데이터를 절대 덮어쓰지 않고 오류 안내.
  3) 가져오기 직전 현재 상태를 메모리 백업 후 적용하며, 사용자에게 **전체 덮어쓰기** 또는 **프로필 단위 병합** 선택을 제공한다.

### 5.4 용량 관리 (`LocalStorage` 5 MB 한계 대응)

1. **정적 마스터 데이터 저장 금지**: `characters.json`(340 KB)과 `normalized_strokes.json`(3.34 MB)은 `localStorage`에 넣지 않는다.
2. **필기 원시 좌표 폐기**: 쓰기 문제에서 `userPoints` 원시 터치 좌표 배열은 실시간 판정 직후 폐기하고, 최종 정오·실패 횟수 등 경량 메타데이터만 `AnswerRecord`에 저장한다.
3. **완료 회차 아카이브 상한**: `completedSessions`는 최근 100회차까지만 세부 `answers`를 보존하고, 그 이전 회차는 일자/단원 요약 통계로 압축하거나 오래된 순으로 정리한다(용량 사용률 80% 초과 시 백업 다운로드 유도 배너 표시).
4. **`QuotaExceededError` 예외 처리**: 저장 시 `DOMException`을 포착해 메모리 상태를 유지하면서 사용자에게 "저장 공간 부족 — JSON 백업 후 오래된 기록 정리" 안내를 띄운다.

- **백업 파일 무결성**: JSON 백업 파싱 시 `Object.prototype` 오염(`__proto__`, `constructor`) 키를 차단하는 순수 파싱·화이트리스트 검증을 적용한다.

### 6.4 2차 서버 전환 마이그레이션 전략

1. **데이터 버전 호환 유지**: 모든 `SessionSnapshot`과 `CompletedSessionRecord`에 `dataVersion` (`"0.2.0"`)과 한자 고유 ID(`hanja-6F22` 형식)를 기록하므로, 추후 단원/급수 데이터가 추가되어도 과거 기록 매핑이 깨지지 않는다.
2. **무손실 클라우드 승격 흐름**:
   - 2차에서 보호자 계정 로그인 도입 후, `LocalStorageAdapter.exportBackup()` 데이터를 읽어 사용자가 선택한 가족 구성원 계정에 1회 업로드(`POST /api/migration/import-local`)한다.
   - 서버는 `exposureStats`(누적 출제 횟수/시각), `reviewQueue`(복습 상태 및 이력), `completedSessions`를 타임스탬프/ID 중복 제거(idempotent upsert) 방식으로 병합한다.
   - 마이그레이션 완료 플래그를 기록해 동일 기기에서 중복 업로드를 방지하고, 이후 `RemoteStorageAdapter`로 전환한다.
